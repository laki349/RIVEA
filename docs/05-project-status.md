## 0-F. 2026-07-31 — 개인화: concern-first IA가 데이터로 작동한다

**정적 export 88페이지** (`/profile` 추가).

「내 피부 고민 설정하기」가 `/category`로 던지고 끝이었다 — 설정하러 들어갔는데 카테고리 목록이 나왔다.
`/check`·`/gift`의 답도 저장되지 않았다. **입력을 받고 아무것도 안 하면 개인화가 아니라 설문이다.**
이 앱이 남들과 다른 이유가 concern-first IA인데, 그게 화면에서 증명되지 않는 상태였다.

- **`src/lib/profile.ts`** — 고민(순서 있는 배열) + 연령대. 계정별 저장(`scope.ts`).
  카탈로그에서 사라진 slug는 읽을 때 버린다 — 없는 고민으로 정렬하면 **조용히 틀린다**.
- **`/profile`** — 고민 7개 다중 선택(선택 순서를 ①②로 표시) + 연령대 3개.
  **저장 버튼이 없다**: 고르는 즉시 저장. 40대+ 대상에서 "고르고 → 저장 누르기"는
  한 단계가 늘어나는 만큼 이탈이 생기고, 되돌리기 쉬운 설정에 확인 단계는 불필요하다.
  대신 **지금 무엇이 반영됐는지 문장으로** 보여준다 — 어디에 쓰이는지 안 보이면 다시 안 온다.

### 반영되는 곳은 홈 한 곳에 모았다
여러 화면에 흩뿌리면 사용자가 무엇 때문에 화면이 달라졌는지 알 수 없다.
- `ConcernRail` — 내 고민이 앞으로. 프로필 없으면 레일 끝에 설정 진입점(배너로 얹으면 상품 흐름을 끊는다)
- `PickRail` — 내 고민의 루틴이 먼저
- `CohortSection` — 내 연령대 탭으로 열림. **사용자가 탭을 직접 만지면 그 선택이 이긴다**(`touched`)

⚠️ **순서만 바꾸고 빼지 않는다.** 고른 고민 밖의 상품이 사라지면 둘러보기가 막히고,
고민이 하나뿐인 사용자에게는 앱이 텅 빈 것처럼 보인다.

⚠️ **프로필을 `useState` 초기값으로 쓰면 안 된다.** 정적 렌더 시점엔 빈 값이라
하이드레이션 불일치가 난다. `useEffect`로 적용한다.

**`/gift`는 프로필에 저장하지 않는다** — 딸이 어머니 고민을 입력하는 화면이라
구매자 본인의 프로필로 저장하면 틀린 데이터가 된다.

**실측**: 모공 → 두피·헤어 순서로 선택 + 60대 이상 → 홈 고민 레일이 `모공 · 두피·헤어` 순,
Pick이 `모공 이중 · 두피 볼륨` 순, 연령 섹션이 "60대가 지금 많이 봐요"로 열림,
마이페이지 요약 `모공 · 두피·헤어 · 60대 이상`. 콘솔 에러 0.

## 0-E. 2026-07-31 — 상품 공유 (§5-3 「메타데이터 전역 1개」 해소)

**공유의 대상은 매거진이 아니라 상품·루틴이다.** 카톡으로 상품을 보내는 흐름을 기준으로 잡았다.
비어 있던 건 두 쪽 모두였다.

**① 보내는 쪽** — 앱 전체에 공유 버튼이 하나도 없었다(주소창 복사만 가능).
→ `ShareButton.tsx`: `navigator.share`(폰의 OS 공유 시트, 카톡 포함) → 없으면 **클립보드 복사 폴백**.
카카오 SDK를 안 쓴 이유는 JS 키를 클라이언트에 박아야 하고 도메인 등록이 필요한데,
OS 공유 시트가 이미 카톡을 포함하고 정적 배포에 추가 설정이 없다.
`AppBar`에 `share` prop으로 붙였고, **아이콘이 하나 늘면 좌우 폭을 같이 늘려야 제목이 안 밀린다**(72→108px).

**② 받는 쪽** — 링크를 받은 사람이 `/product/p1`을 열면 **상품이 아니라 온보딩(스플래시→로그인)을 봤다.**
정적 HTML엔 내용이 있어서 크롤러는 읽는데 사람은 못 읽는 상태.
→ `Onboarding.tsx`에 `OPEN_PREFIXES`(`/product/ /routine/ /magazine/ /concern/ /brand/`) 제외.
**표준 패턴 = 콘텐츠 공개, 커머스 로그인.** `ready` 전에도 스플래시를 깜빡이지 않게 처리했다 —
그 한 순간이 링크를 받은 사람에게는 "잘못 열렸나" 싶은 화면이 된다.

### 메타데이터
- `layout.tsx`에 **`metadataBase` 필수** — 없으면 og:image가 상대경로로 나가 **카드가 비어 보인다**
- `title.template: "%s · 리베아"` — 이게 없으면 87페이지가 전부 같은 제목
- `product/[id]`·`routine/[id]`에 `generateMetadata`. 서버 컴포넌트 + `generateStaticParams`라
  정적 export에서도 각 HTML의 `<head>`에 그대로 구워진다 (빌드 산출물로 확인)
- `sitemap.ts`(67개 URL)·`robots.ts` 신설. 개인 화면(장바구니·결제·주문·마이페이지·찜)은 색인 제외

⚠️ **가격을 og description에 넣었다.** 커머스 공유에서 가장 궁금한 값이라 넣었지만
**카톡이 카드를 캐시하므로 가격을 바꾸면 옛 카드가 한동안 남는다.** 실서비스에선 캐시 갱신이 필요하다.

**실측**: 세션·localStorage를 비운 "링크를 처음 받은 사람" 조건에서 `/product/p1` 직접 진입 →
온보딩 없이 상품 표시, 탭 제목 `라비드 멜라 리페어 세럼 30ml · 리베아`, 공유 클릭 시 "링크를 복사했어요".
빌드 산출물 `out/product/p1.html`에 og:image가 `https://rivea-app.web.app/...` 절대 URL로 존재.

## 0-D. 2026-07-31 — 로그인이 상태를 바꾼다 (계정별 저장 + 게스트 승계)

예전엔 장바구니·찜·주문이 브라우저 단위 키 하나에 있어서 **로그인 전후가 완전히 동일**했다.
얻는 게 없는 로그인은 장식이고, 한 폰을 모녀가 같이 쓰면 서로의 장바구니가 섞인다.

- **`src/lib/scope.ts`** — localStorage를 uid별로 나눈다. 스코프가 바뀌면 등록된 스토어가 일괄 재로드.
  스코프 도입 전 키(`rivea-cart`)는 **첫 진입에서 그 uid 것으로 이관**(한 번만) — 담아둔 게 사라지면 안 된다.
- **승계(link) vs 병합(merge)** — 새 계정을 만들 때는 `linkWithCredential`/`linkWithPopup`으로
  **익명 uid를 그대로 승격**시킨다. uid가 유지되니 옮길 데이터가 없다.
  이미 있는 계정으로 로그인할 때만 uid가 바뀌어 병합한다.
  장바구니 수량은 **합산이 아니라 큰 쪽** — 합산하면 양쪽 2개가 4개가 돼 의도 없는 수량이 된다.
- **`AuthScope`**(레이아웃) — 인증 상태를 스코프에 연결. 없으면 로그인해도 스코프가 안 바뀐다.
- **잡은 순서 결함**: 로그인은 ①인증 변경→스코프 이동(빈 데이터 읽음) ②병합, 두 단계라
  ②의 결과를 화면이 몰라 **합친 장바구니가 새로고침 전까지 안 보였다** → `refreshScoped()`.

### 포인트·쿠폰·등급 (`src/lib/wallet.ts`)
결제 화면이 "보유 3,200P·쿠폰 2장"을 하드코딩으로 띄우고 **금액에서 실제로 차감했는데**
마이페이지 잔액은 영원히 그대로였다. 숫자가 안 맞는 순간 화면 전체가 시늉으로 읽힌다.
- 잔액은 계정별 저장, 주문 시 차감 + 적립, **취소 시 환원**
- 적립액은 재계산하지 않고 `Order.earned`에 **저장**한다 — 그 사이 등급이 오르면
  계산값이 커져서 취소가 이득이 되는 구멍이 생긴다
- 등급·누적 구매액은 주문에서 파생(배송 상태와 같은 이유로 저장하지 않는다)

**실측**: 3,200P 사용 → 24,500 → **21,300원** 결제 → 잔액 **213P**(1% 적립),
마이페이지 누적 21,300원 · 78,700원 더 구매 시 GOLD. 다른 uid 키를 심어도 현재 세션은 보지 않음.

🔴 **미검증 1건**: 게스트→회원 **승계**는 실제 회원가입이 필요해 실측하지 못했다.
`/login` 회원가입으로 가입한 뒤 마이페이지 값(주문·포인트·누적)이 남아 있으면 승계 성공.

### Firebase Auth 프로비저닝 완료
익명·이메일/비밀번호·Google 3개 켜짐. 승인된 도메인에 `localhost`·`rivea-app.web.app` 확인.
게스트 진입이 폴백(`rivea-local-browse`) 없이 실제 uid를 발급받는다 — §5-1 해소.

## 0-C. 2026-07-31 — 주문 루프를 닫았다 (§5 「주문내역 미구현」 해소)

**정적 export 87페이지** (`/orders`, `/orders/detail` 추가).

결제를 끝낸 사용자가 **자기 주문을 다시 볼 방법이 없던 게** 앱을 데모로 읽히게 하던 1순위였다.
`order/complete`가 주문번호를 `useEffect`에서 만들어 화면에만 찍고 버렸고, 바로 아래
"주문 내역 보기" 버튼이 보내는 마이페이지 「주문·배송」은 동작 없는 `<button>`이었다.

### 새 파일 2개

- **`src/lib/orders.ts`** — `cart.ts`/`wish.ts`와 같은 패턴(localStorage + `useSyncExternalStore`).
  주문은 **카탈로그 참조가 아니라 스냅샷**으로 저장한다(품목명·단가·이미지까지 복사) —
  나중에 가격이 바뀌어도 지난 주문 금액이 흔들리면 안 된다.
  **배송 상태는 저장하지 않고 경과시간으로 파생**한다(1시간/1일/3일 → 결제완료·배송준비·배송중·배송완료).
  값을 박아두면 며칠 전 주문이 영원히 "결제 완료"로 남아 가짜로 읽힌다.
  취소는 `preparing`까지만(`isCancellable`) — 실제 커머스의 취소 가능 구간과 같다.
- **`src/lib/lines.ts`** — 장바구니·결제·주문내역이 공유하는 라인/배송비 계산.

### 같이 잡은 결함 2개 (둘 다 금액이 어긋나던 문제)

1. **선택 해제한 상품까지 결제됐다.** 선택이 장바구니 화면의 로컬 state였고 결제 화면은
   장바구니 **전체**를 읽었다. → `CartItem.checked`로 스토어에 올렸다(기존 저장분은 `load()`에서 true로 마이그레이션).
   결제 후엔 **주문한 줄만** 빠지고 선택 안 한 건 장바구니에 남는다(`clearCart` → `removeMany`).
2. **배송비 규칙이 화면마다 달랐다.** 장바구니는 브랜드별(`freeShippingOver`/`shippingFee`),
   결제는 "5만원↑ 무료, 아니면 3,000원". → `lines.ts`의 `totalsOf()` 하나로 통일.
   중개형이라 배송비는 입점 브랜드가 정하는 값이 맞다.

### 라우팅 주의
정적 export라 `/orders/[no]`를 쓸 수 없다. **`/orders/detail?no=...` 쿼리 + `useSearchParams`**
(+`Suspense` 경계) — `category/[slug]`와 같은 처리. `docs/01:99`의 `/order/[id]` 계획을 이렇게 대체했다.

**실측 검증** (dev, 375px): 담기 2건 → 1건 선택 해제(72,500 → 48,000) → 쿠폰 적용(38,000) →
결제 → 완료 화면에 실제 주문번호·도착예정 → 상세 → 취소까지 클릭으로 확인. 콘솔 에러 0.

⚠️ 서버가 없으므로 **주문은 그 브라우저에만 존재한다.** 상세 화면에 "다른 기기에서는 보이지 않아요"
폴백을 뒀다. Firestore로 옮길 때 `orders.ts` 함수 시그니처만 유지하면 화면은 그대로 쓴다.

  375px에서 오버플로 없음 (로고 63 + 매거진 36 + 루틴확인 52 + 검색 32 + 장바구니 32)
- `/gift` → **마이페이지 › 쇼핑 › 선물하기**. 커머스 하위 기능이라 여기가 자연스럽다

### `/check` — 성분·순서 검사기

쓰는 제품을 고르면 **아침·저녁·주1~2회 순서표 + 판정**을 낸다. 판정마다 "왜 그런가요" 근거를 같이 띄운다.

**규칙 엔진(`src/lib/rules.ts`)이고 LLM이 아니다.** 이유: 피부에 바르는 제품의 병용 판정에서
환각이 나오면 사용자가 다친다. AI를 얹을 자리는 `explain()` 한 곳으로 남겨뒀고,
**판정은 고정하고 문장만 다듬는 용도로만** 써야 한다 (파일 주석에 명시).

핵심 축 두 개:
- **순서** — LED는 빛이 통과해야 하니 **바르기 전**, 갈바닉은 성분을 밀어 넣으니 **바른 후**.
  이 둘이 정반대인데 어느 설명서에도 나란히 안 적혀 있다. 이게 이 기능의 실질적 가치.
- **병용** — 레티놀×AHA/BHA 겹침 경고, 나이아신아마이드 중복(함량 합산으로 판정),
  나이아신아마이드+트라넥삼산 궁합, 색소 관리 중 선크림 누락 경고, 고주파 후 장벽 성분 유무

**우리가 안 파는 제품도 검사한다** (`externalItems`: 레티놀·AHA/BHA·고농도 비타C·타 브랜드
나이아신아마이드·선크림). 우리 카탈로그 안에서만 보면 충돌이 안 나서 기능이 시늉이 되고,
남의 제품을 봐주는 것 자체가 「브랜드 중립」(docs/07 §8)의 실질이다.

규칙 판정용으로 `Product.actives`(성분 키+공개 함량)·`Product.deviceKinds`를 추가했다.
`keyIngredient` 문자열은 표시용이라 판정에 쓸 수 없다.

**잡은 버그 3개** (전부 실제 동작 확인 중 발견): 복합기(울트라튠)가 아침·저녁에 중복 출현 /
각질 제품이 저녁·주간에 중복 / LED "바르기 전" 규칙이 젤 기반 복합기에도 적용됨.
→ `deviceSlot()` 한 곳에서만 자리를 정하도록 고쳤다. **여러 규칙이 각자 push하면 중복이 난다.**

### `/gift` — 대리구매(딸) 진입점

docs/07 §9의 획득 전략. 3단계: 어머니 연령대 → 고민 아는지 → 예산 → 루틴 추천.

**핵심은 "잘 몰라요" 분기다.** 딸은 엄마 피부 고민을 모른다. 여기서 막다른 길로 두지 않고
**엠브레인 2022 조사 수치로 대신 답한다** (출처를 화면에 표기). 눌러서 기준 변경 가능.

⚠️ **데이터 정확성 주의** — `cohortTop`은 반드시 pct 내림차순이어야 하고,
docs/07 §2가 **연령대로 쪼개 주는 항목은 「피부 잡티」와 「탄력 저하」 둘뿐**이다.
모공 60.5%는 전 연령 합계 수치라 연령별 차트에 섞으면 오독을 만든다 — 그래서 뺐다.
(처음에 50대 1위를 탄력 저하로 넣었는데 잡티 76.6% > 탄력 70.9%로 수치와 어긋나 수정함.
연령을 실제로 가르는 건 "어디서 정점인가"이고, 그건 `cohortInsight` 문장으로 따로 표시한다.)

기존 4개는 "성분 역할 분담" 논리였고, 신규 6개는 여기에 **순서(order)** 축을 추가했다.
**이게 앱의 실질적 정보 가치다** — 어느 앱도 기기와 화장품의 순서를 정리해주지 않는다.

| id | 제목 | 근거 |
|---|---|---|
| r5 | 기미엔 성분 하나로는 부족해요 | 나이아신아마이드(멜라닌 전달 차단) + 트라넥삼산(생성 신호 앞단) = **경로가 다름** |

| r8 | 고주파 쓴 날은 장벽부터 채워야 해요 | RF 열 → 수분 손실 → 세라마이드·판테놀로 회복 |

| r10 | 모공은 조이는 것과 붙드는 것 둘 다 | 40대 모공은 확장보다 탄력 저하로 늘어나는 쪽 |

### 비교표 (docs/07 수정안 5·6 + 공정위 「비교표시·광고에 관한 심사지침」)
- 디바이스에만. **화장품 상세에서 제거됨** (저관여 소비재라 비교가 판단을 돕지 않음)
- 축 2개(작동 방식·무게) + 가격. 비교 기준·확인 시점을 화면에 명시
- 다른 브랜드 우선 정렬 — 같은 브랜드 라인업만 비교하면 「브랜드 중립」이 증명되지 않음
- 우열 판단 문구 없음. 효능·효과는 비교 대상에서 배제

### 지킨 선 두 개 (건드리지 말 것)
1. **효과 표현을 specs에 옮기지 않았다.** 다나와에 "주름개선·탄력개선"으로 표기돼 있어도 배제 —
   2019년 식약처가 비의료용 LED 마스크 **48개 제품에 시정명령**을 낸 사유가 정확히 이것.
   specs는 방식·파장·무게·시간 등 측정 가능한 물리량만.
2. **브랜드 제품 사진을 쓰지 않았다.** 저작물이고 이 앱은 공개 배포된다(rivea-app.web.app).
   `image` 필드로 자체 생성 이미지 21장을 제품 유형별로 재사용 — 해당 제품의 실제 사진이 아니다.
   고유 이미지가 필요하면 `docs/04` 프롬프트로 생성해 `image` 값만 갈아끼우면 된다.

홈 하단에 데모 고지 유지: "발표용 데모이고 실제 판매·결제는 이뤄지지 않아요. 리뷰·평점·조회수는 예시 수치."

### 🔴 남은 확인 사항
**품목별 의료기기 허가 여부.** LG 더마 LED 마스크만 `non-medical` 확인(국가기술표준원 비의료용
예비안전기준 통과), 나머지 7종은 `deviceClass: "unknown"`. 의료기기 광고는 사전심의 대상이라
실서비스 전 식약처 의료기기 전자민원창구에서 개별 확인 후 `"medical"` 품목은
`comparableDevices`에서 제외해야 한다. 현재는 물리 사양·가격만 비교하고 효능을 안 다뤄 위험을 낮춘 상태.

## 5. 발견된 결함 (실측, 2026-07-30)

### 🔴 즉시 조치 필요

**5-1. Firebase Auth가 프로비저닝 안 됨** — ✅ **2026-07-31 해소 (§0-D)**
익명 로그인 시 `CONFIGURATION_NOT_FOUND`. **콘솔에서 켜야 하고 코드로는 불가.**
→ https://console.firebase.google.com/project/rivea-app/authentication 에서 **시작하기** 누르고
Sign-in method 탭에서 **이메일/비밀번호 · Google · 익명** 3개 켜기. 재배포 불필요.
현재는 폴백(`rivea-local-browse` 플래그)으로 앱이 죽지는 않음.

**5-2. 매거진이 온보딩에 막혀 있음** — ✅ **2026-07-31 해소 (§0-E).** 상품·루틴·고민·브랜드까지 함께 열었다
검색이나 카톡으로 `/magazine/[slug]`에 들어온 사람이 **기사가 아니라 온보딩을 본다.**
정적 HTML에는 본문이 있어서 **크롤링은 되는데 사람은 못 읽는다.**
→ 조치: `Onboarding.tsx`에서 `/magazine/*` 경로는 오버레이 제외 (약 10줄).
표준 패턴 = 콘텐츠 공개, 커머스 로그인.

**5-3. 메타데이터가 전역 1개뿐** — ✅ **2026-07-31 해소 (§0-E).** 상품·루틴 og + sitemap + robots
54페이지 전부 `<title>RIVEA — 리베아</title>`. 기사별 `generateMetadata` 없음.
`sitemap.xml`·`robots.txt`·`og:image` 전부 없음.
→ **og 태그가 없으면 카톡 공유 시 미리보기 카드가 안 뜬다.** 유통 전략의 전제가 깨져 있음.

### 🟡 접근성 — 문서가 "최우선"이라 선언한 것과 실측이 어긋남

`docs/03-design-system.md`는 "본문 16px 이상, 12px 미만 금지, 터치타깃 ≥44px, AA 확보"라고 명시.
실측 결과 (배포본, 390x844):

| 항목 | 실측 | 기준 |
|---|---|---|
| 11px 텍스트 | **18곳 (홈에서 최다 크기)** | 12px 미만 금지 |
| 16px 이상 | 13곳뿐 | 본문 16px+ |
| 비활성 탭바 라벨 대비 | **2.35:1** | 4.5:1 |
| `text-meta`(#8B8279) 대비 | 3.56~3.77:1 (14곳) | 4.5:1 |
| 터치타깃 미달 | **14곳** (제품/루틴 탭 24×29 등) | ≥44px |

**Quick fix (각 30분 이내, 전부 토큰/CSS)**
1. `text-meta` `#8B8279` → `#6B635C` — **한 토큰 교체로 대비 위반 대부분 해소** (3.56 → 약 5.4:1)
2. 비활성 탭바 라벨 `text-disabled` → `text-meta`
3. 11px → 12px 일괄, 탭바 라벨 13px
4. 연령 칩·제품/루틴 탭 34/29px → 44px

### 🟡 위계 — 디자인이 전략을 말하지 않음

섹션 제목이 **전부 17px/700 동일**. 차별화 섹션과 범용 섹션이 동급.

```
리베아's Pick   17px/700   ← 차별화 상품
베스트          17px/700   ← 범용
신상            17px/700   ← 범용
고민으로 찾기    13px/700   ← 전략적 관문인데 가장 작음
```

홈만 볼드 과다: **700이 64개 vs 400이 50개** (상품상세는 400:37/700:17로 정상).

→ 리베아's Pick 20px / 고민으로 찾기 17px 승격 / 홈 카드 상품명 700→500

### 🟢 죽은 UI

- **"전체보기"가 링크가 아닌 곳 4개** — 고민상세, 상품상세 리뷰, 카테고리, 연령인기 (전부 `<span>`)
- **마이페이지 죽은 항목 9개** — 최근 본 상품 / 재구매 목록 / 배송지 관리 / 1:1 문의 / 공지사항 /
  자주 묻는 질문 / 체험단 / 리뷰 이벤트 / 쿠폰 받기. 전부 `<button>`에 동작 없음.
  → **전부 만들 게 아니라 줄여야 함.** 죽은 메뉴 9개는 살아있는 3개보다 나쁨
  → 메뉴 항목이 `{ label, href? }` 구조로 바뀌었으니(§0-B) **href 없는 항목을 지우기만 하면 된다.**
  현재 `쇼핑` 그룹은 살아있는 「선물하기」 1개 + 죽은 3개라 대비가 오히려 도드라진다
- ~~**주문내역 미구현**~~ → ✅ **2026-07-31 해소. §0-C 참고** (`orders.ts` + `/orders`,
  마이페이지 「주문·배송」이 실제 주문 개수를 표시하는 링크로 바뀜)

## 6. 재배포 방법 (이미지/코드 수정 후)

```bash
cd "/Users/jinsihu/Desktop/workplace/mature care"
npm run build                                          # out/ 재생성 (필수! 빠뜨리면 이전 빌드가 배포됨)
npx -y firebase-tools@latest deploy --only hosting --project rivea-app
```

**주의 사항 (겪었던 삽질들)**:
- **`npm run dev`가 켜진 상태로 `npm run build`를 돌리면 안 된다.** 프로덕션 빌드가 `.next`를
  다시 쓰면서 dev 서버가 쓰던 `vendor-chunks`·static 청크를 지운다. 증상은
  `Cannot find module './vendor-chunks/next.js'` + `layout.css` 404 → **CSS가 전부 빠진 화면**.
  코드 결함처럼 보이지만 아니다. 해결: dev 서버 재시작 (빌드 전엔 dev를 끄는 게 안전)
- `firebase_init`(MCP 도구)을 다시 돌리면 `out/`에 Firebase 기본 웰컴 템플릿을 덮어씀 → 배포 전 `npm run build` 다시 하면 해결
- 이미지처럼 대용량 파일 많을 때 firebase-tools 배포가 `Body has already been read` 에러로 실패할 수 있음 → 재시도하거나 이미지 용량 줄이기 (지금은 1000px/품질78로 이미 최적화됨, `public/images` 총 2.2MB)
- MCP `firebase_deploy` 도구가 "no site name" assertion 에러를 냄 → CLI 직접 실행(`npx firebase-tools deploy`)이 더 안정적
